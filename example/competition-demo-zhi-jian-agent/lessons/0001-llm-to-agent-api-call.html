从 LLM 到 Agent：一次 API 调用缺了什么

逐行解剖一次最小的对话 API 调用，练习自己写出并解释关键代码；再看本例尚未实现的历史、工具与上下文管理机制，理解工具型 Agent 如何补足它们。

先修：能读基本 Python本课目标：解释并改写调用代码

展示课 · 内容经人工校核；续课依据你在本目录填写的新作答。

学习目标

  1. 逐行读懂一段最小的对话 API 调用代码，说出 messages、role 与「无状态」各自的含义。
  2. 说出本课无工具、未关联会话示例的三个局限，并解释工具型 Agent 可增加哪些机制。
  3. 区分 system 与 user 消息在信任上的差异，并说明它与提示注入的关系。

先修说明：只需要能读懂 Python 的变量、函数调用和列表/字典写法；不需要任何 Agent 或框架经验。

课首回忆：先写下你现在的印象

会调用接口与能解释它的工作方式，是两个不同目标。今天先拆解一个最小示例，再检验能否改写消息结构，最后比较本课程的工具型 Agent 多了什么。

往下读之前，先凭印象作答，再与课末回答对照。记录哪些地方能独立解释、哪些地方需要提示，帮助下一课决定讲多细。

课首回忆（先作答再往下读）

调用对话 API 时，你发给模型的最核心的东西是什么？它大概长什么样、包含哪些部分？两三句话即可，记不住就写「记不住」——这比编造有用得多。

一次调用到底发生了什么

先把本课的 Chat Completions 文本示例当成一张图看。你的程序（左边）发送本次请求所需的 messages，模型服务（右边）返回结果。下一次独立请求不会自动继承这次对话；这不等于服务商绝不保留请求记录，后者取决于具体服务的接口与数据政策。

本课第一个心智模型：在这个无工具、未关联会话的 Chat Completions 示例中，本次发送什么，模型本次就能看见什么；下一次独立请求要再次提供所需上下文。

本例没有提供工具，因此它只请求文本回复，不会自行查库、发邮件或读文件。支持工具调用的接口也可能在单次请求中返回工具调用意图；实际执行与授权仍由应用或服务环境控制。后面会把这条边界画清楚。

最小代码逐行解剖

下面用 11 个讲解点拆解最小文本调用；实际运行需安装 SDK、配置有效密钥并保证服务可用。纸面阅读和练习不需要这些条件：

import os                                    # ① 标准库：用来读环境变量
from openai import OpenAI                    # ② OpenAI SDK；此例使用 DeepSeek 的兼容接口

client = OpenAI(                             # ③ 创建客户端：告诉 SDK 用谁的钥匙、找谁的服务
    api_key=os.environ.get("LLM_API_KEY"),   # ④ 去环境变量里取密钥，代码里只有名字
    base_url="https://api.deepseek.com",     # ⑤ 服务地址：DeepSeek，用其他厂商就改这里
)

response = client.chat.completions.create(   # ⑥ 发起一次调用
    model="deepseek-flash",                  # ⑦ 指定模型名，不同厂商名字不同
    messages=[                               # ⑧ 核心参数：消息列表，按对话顺序排列
        {"role": "system", "content": "你是一个简洁的技术助手。"},   # ⑨ system：给模型的岗位说明书
        {"role": "user", "content": "用一句话解释什么是 API。"},     # ⑩ user：本轮的问题
    ],
)

print(response.choices[0].message.content)   # ⑪ 从响应结构里取出模型生成的文本

第一组：钥匙与地址（③④⑤）

OpenAI(...) 构造的是一个「客户端」对象——它本身还没联系任何服务，只是记住了两件事：用哪把钥匙（api_key）和找谁的服务（base_url）。

第 ④ 行从环境变量读取密钥，避免在源码中硬编码；设置方式、日志、截图与进程环境仍可能泄露它。第 ⑤ 行指定服务地址，换服务时需核对模型名、鉴权与参数兼容性。

易错点：把真实密钥直接写进源码、命令或聊天都可能泄露。练习时用不回显输入设置当前会话的环境变量；生产项目使用适当的密钥管理方式，不提交、截图或打印密钥。

第二组：内容（⑧⑨⑩）

在本课的基础文本示例中，messages 是消息列表，每条消息至少说明角色与内容。本课先认识两种角色：

  • system：开发者写给模型的整体指令——角色、风格、边界。它是「岗位说明书」，每次调用都随消息列表一起发送。
  • user：本轮使用者的输入，也就是这次要模型处理的实际问题。

消息列表保留了谁提供内容、哪些是助手回复等角色信息。role 不能单独判定每句话是否有权指挥动作；用户消息也可能包含引用资料。应用还应区分获授权任务与待处理内容。

第三组：取结果（⑪）

这个普通文本回复可从 response.choices[0].message.content 读取。choices 是候选结果列表，[0] 取第一项；用量统计属于响应的其他字段。若返回工具调用或其他类型结果，不能一概按此表达式取文本。

把它跑起来（可选，环境就绪时）

想现在就亲手跑通，需要三步：装 SDK、设环境变量、运行脚本。Windows PowerShell 里前两步是：

python -m pip install openai
$secret = Read-Host "请输入 API Key（不会回显）" -AsSecureString
$env:LLM_API_KEY = [System.Net.NetworkCredential]::new("", $secret).Password
Remove-Variable secret

这只为当前 PowerShell 会话及其子进程提供密钥，不会把密钥字面值写进命令历史；环境变量仍可能被同机进程或调试工具读取。不要在共享终端操作，练习结束后关闭该窗口。

然后把上面的 Python 代码存成 first_call.py，在设置了环境变量的终端里运行 python first_call.py。没有可用的 API Key 也不影响本课——后面的纸面练习已覆盖全部核心概念，实操标注为「待环境就绪后验证」即可。

即时检查 1 · system 消息的作用

在这段最小程序里，「你是一个简洁的技术助手。」这条消息的作用是什么？

无状态：模型不记得你

图 1 的红框说的是本示例的上下文传递，不是服务端的数据留存政策。每次独立发起请求，下一次不会自动带上前次问答。若第一轮提供姓名，第二轮只问“我叫什么”，请求就缺少姓名依据；程序需提供相关历史。支持会话关联的接口可能采用另一种管理方式。

这带来一个初学者最常见的意外。看两种做法的对比：

写成代码，第二轮调用的消息列表长这样（注意 assistant 那条是谁放进去的）：

messages = [
    {"role": "system", "content": "你是一个简洁的技术助手。"},
    {"role": "user", "content": "我叫小林，正在学习 Agent 开发。"},
    {"role": "assistant", "content": "你好，小林！很高兴陪你学 Agent。"},   # 示例中由程序保存后追加的上一轮回答
    {"role": "user", "content": "我叫什么名字？"},                       # 本轮新问题
]

response = client.chat.completions.create(model="deepseek-flash", messages=messages)
print(response.choices[0].message.content)   # 可能回复：你叫小林；实际生成须运行核验。

关键点：在本例中，第三行 assistant 消息是程序保存上一轮回复后加入新请求的，不是模型凭空记起的。这里的多轮上下文由程序维护的 messages 提供；不要把这个实现方式推广成所有 API 都不提供会话状态或不保留数据。

本课第二个心智模型：在这个 Chat Completions 示例中，程序选取并传入历史消息实现多轮上下文；历史变长后还要决定保留、摘要或检索什么。第 3 课会专门处理这一点。

即时检查 2 · 无状态的后果

你的程序连续调用两次对话 API。第二次只传了本轮的新问题，没有把第一轮的问答放进 messages。模型最可能的表现是？

一次调用缺了什么：Agent 的补足

把本课最小示例的限制合起来看：下一次独立请求不自动带历史，本例没有工具，上下文窗口也有限。工具型 Agent 可以在应用层加入历史选择、工具执行和记忆管理；这些不是所有单次 API 请求固有的缺陷，也不是每个 Agent 都必须采用同一种实现。

逐个说清补足关系：

  1. 不自动带历史 → 程序管理上下文。应用选取当前步骤需要的输入、输出和历史片段，放入下一次请求；并非无限保留所有消息。图 2 下框展示的是最小做法。
  2. 本例无工具 → 加入受控工具调用。模型提出工具与参数，应用检查后执行，再回填结果；停止由任务完成、预算与必要的人审共同约束。
  3. 装不下 → 上下文与记忆管理。有限窗口不能无限追加；应用需要选择历史、外部保存与检索方式。记忆是后续候选主题，不是工具型 Agent 的唯一实现要求。

本课程重点实现的工具型 Agent，以模型参与决策，在循环中选择工具或下一步，利用执行结果调整后续动作，并受明确的停止与权限条件约束。这是本课程采用的架构范围，不是所有被称为「Agent」的系统的唯一判准。

注意边界：有循环和工具的系统才是本课程讨论的 Agent；单次调用、或固定流程串联几次调用（无自主决策）的「工作流」，能力与风险都不同。这个区分在 Phase 1 后段和资源导学里会再出现。

信任的裂缝：system 与 user 不是平等的

前两节都在讲「怎么让它工作」，这一节讲 Mission 的另一半——风险从哪里开始。你已经知道 system 是上层指令，user 是较低优先级的输入；网页和文档内容通常是要处理的数据。

角色有指令优先级，但不能把它当成执行权限隔离。在 OpenAI 的消息规范中，system/developer 指令高于 user 指令；不可信网页或文档文本不应因此获得上层权限。模型仍可能受其中的诱导文字影响，所以应用还需限制工具权限、验证参数，并对高风险动作设置确认。

按注入入口分两类，各用一句话记住：

  • 直接注入：攻击文本来自使用者自己的输入——对话框里直接写「忽略之前指令」。这是你在图 4 下框看到的形态。
  • 间接注入：攻击文本藏在模型要读取的外部内容中，如网页、文档、邮件和数据库字段；使用者可能并未察觉。

为什么对 Agent 要特别当心？即使没有工具，注入也可能污染答案或诱导泄露已提供的信息；若应用还授予工具权限，错误动作可能进一步影响文件、网络或账户。你的项目计划读取外部情报，网页与文档中的间接注入是需要重点评估的攻击面；实际后果取决于工具权限与应用的防护。

本课只建立「裂缝存在、位置在哪」的意识。怎么防守——最小权限、工具分级、输出审查——是 Phase 2 的主战场，从「提示注入攻防」一课正式开始。

练习 1 · 改善三处写法

目标是安全地调用对话 API，并只显示模型生成的摘要。找出下面 3 处不符合目标的写法：密钥管理、参数结构、结果呈现。写下怎么改（纸面即可，不用运行）：

from openai import OpenAI

client = OpenAI(
    api_key="DEMO_KEY_NOT_VALID",
    base_url="https://api.deepseek.com",
)

response = client.chat.completions.create(
    messages="请帮我总结这段漏洞情报",
    model="deepseek-flash",
)

print(response)
查看提示

分别检查客户端的密钥来源、messages 参数的类型、最后打印结果的那一行。对照本课 ①–⑪ 编号逐行检查。

查看答案与解析

错误 1（密钥硬编码）：DEMO_KEY_NOT_VALID 是无效教学占位。真实密钥不应写进源码；改为读取环境变量，并导入 os。硬编码可能让分享和提交代码变成泄露通道。

错误 2（messages 类型错误）：messages="请帮我总结这段漏洞情报" 传了一段字符串。修正为消息列表：

messages=[
    {"role": "system", "content": "你是漏洞情报摘要助手。"},
    {"role": "user", "content": "请帮我总结这段漏洞情报"},
]

对应第 ⑧⑨⑩ 行：对话 API 的内容参数是结构化消息列表，不是裸文本——角色边界必须保留。

改善 3（结果呈现）：print(response) 本身是合法的 Python 写法，但打印整个响应对象，不符合“只显示摘要”的目标。改为 print(response.choices[0].message.content)。对应第 ⑪ 行。

再检查：消息参数可能立即报错，但密钥硬编码未必触发异常。代码能运行不代表密钥管理正确；本题假密钥也不会真的鉴权成功。

练习 2 · 迁移：为情报 Agent 写第二轮 messages

这是安全情报项目的纸面模拟。编号 CVE-2026-12345 与下列描述仅作教学占位，不关联真实漏洞。假设程序已保存第一轮消息：

  • system 消息是：你是一个简洁的安全情报分析助手。
  • 第一轮 user 问题：CVE-2026-12345 是什么漏洞？
  • 模型第一轮的回答（已被你的程序保存）：CVE-2026-12345 是某 Web 框架的反序列化漏洞，可导致远程代码执行。

现在使用者追问：「它影响的版本范围是什么？」请写出第二轮调用的完整 messages 列表（Python 写法或 JSON 都行，写在纸上或编辑器里——课末证据框会收集你的最终版本）。

查看提示

问自己：第二轮的列表里应该有几条消息？每条的 role 是什么？assistant 那条是谁放进去的？对照图 2 下框。

查看答案与解析 
messages = [
    {"role": "system", "content": "你是一个简洁的安全情报分析助手。"},
    {"role": "user", "content": "CVE-2026-12345 是什么漏洞？"},
    {"role": "assistant", "content": "CVE-2026-12345 是某 Web 框架的反序列化漏洞，可导致远程代码执行。"},
    {"role": "user", "content": "它影响的版本范围是什么？"},
]

为什么：四条消息按对话顺序排列——system 原样保留（每轮都发）、第一轮 user、第一轮 assistant（由你的程序保存后追加，不是模型自己存的）、本轮新问题。

上下文检查：遗漏 assistant 那条会丢失上一轮回答的内容。不过前面的 user 消息仍有漏洞编号，模型不一定失去指代对象。完整传入相关历史，是为了让追问能衔接前文；历史里的模型回答也仍须核实，不能当作可靠漏洞事实。

本课总结

合上页面后，你应该能凭这三句话复述本课：

  1. 本例的一次调用只发送当前提供的消息；下次独立请求不自动继承这些消息。服务商是否留存数据是另一个问题。
