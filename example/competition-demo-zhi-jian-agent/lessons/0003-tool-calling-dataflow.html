工具调用机制：让模型「动手」的完整数据流

第二课的演示疑问是：「模型返回的工具调用、应用执行工具、把结果提供回模型，这三步之间如何连接？」本课用 messages 列表连接这些步骤，把五步数据流拆开、画出来，再在纸面和本地脚本上各走一遍。

依据：第 2 课作答与疑难全程纸面 + 本地模拟不需要网络与密钥

推进分支展示 · 基于人工修订的第二课与新合成答案生成；正文已校核，不代表真实学员完成或长期掌握。

学习目标

  1. 讲清工具调用的五步数据流：Schema 声明 → 模型决策（tool_calls）→ 程序解析执行（含执行前核对）→ 结果回填（tool 消息）→ 循环与停止条件；并回答「三步靠什么连接」。
  2. 写出工具的 tools 声明（JSON Schema），并在纸面上完成一次完整的消息列表演变：从 [system, user] 到含 assistant 提议与 tool 结果的完整列表。
  3. 把第 2 课的执行前核对嵌入第 3 步执行层：预测「模型提议白名单外目标」时数据流每一层各做什么。

先修：第 1 课（无状态与 messages）、第 2 课（提议不等于执行授权）。本课全部示例为纸面设计与本地模拟，不调用真实 API、不发邮件、不访问网络——正好匹配你说明的环境条件。

课首回忆（先作答再往下读）

① 第 1 课说 Agent 在一次调用之外补了三样东西，是哪三样？② 第 2 课的结论「提议不等于执行授权」——模型提议调用工具之后，谁去执行？执行之前要过什么关？

先回答你的疑问：三步之间靠什么连接

你的问题可以画成一句话：在本课的 Chat Completions 示例中，程序用 messages 保存提议与结果，并用 tool_call_id 配对，再发起下一次请求。messages 承载上下文，程序负责调度，调用编号负责关联。拆开看：

  1. 模型「返回工具调用」，返回的是什么？不是执行，而是一条特殊的 assistant 消息：普通回答的 content 里是文字，这条消息的 content 常为空，另带一个 tool_calls 字段——里面是结构化提议：想调哪个函数（name）、参数是什么（arguments，一段 JSON 文本）、这次提议的编号（id）。
  2. 程序执行，依据是什么？程序按 name 找到注册的处理函数，解析并验证参数，过执行前核对后执行。本课处理函数在你的电脑上运行；实际应用也可以把执行放在服务器或隔离环境中。返回调用提议本身不等于工具已执行。
  3. 结果怎么「提供回模型」？把两样东西追加进同一个 messages 列表：先追加那条含 tool_calls 的 assistant 消息（模型自己说过的话要留档），再追加一条新角色的消息——role: "tool"，带上对应的 tool_call_id，content 是执行结果。然后带着完整列表再次调用 API。模型看到的从来不是「内存里的连接」，而是又一次完整的消息列表——这正是第 1 课无状态的直接延续。

一句话答案：本课靠程序调度、消息上下文和调用编号连接三步：提议写入 assistant 消息，结果写入与它配对的 tool 消息，再请求模型。其他接口可能用不同条目或服务端会话引用承载上下文；学通用职责时，不必记成只有一种实现。

逐步讲解：五步各写什么

场景沿用你的毕业项目：安全情报 Agent。本课用 search_cve 查询和 send_report 发送模拟说明数据流。下面各小段用于理解结构，不是可直接拼接的完整程序；可独立运行的版本在下一节。CVE-2026-12345 仅作编号占位，版本和严重等级均为虚构教学数据，不对应真实漏洞情报。字段采用 Chat Completions 格式，真实接入须核对服务商和模型支持。

第 ① 步：声明工具——给模型一份「菜单」

请求时多传一个 tools 参数：每个工具用 JSON Schema 说清「叫什么、干什么、要什么参数」。这份声明会随每次请求发送（也计入输入 token）：

tools = [
    {
        "type": "function",
        "function": {
            "name": "search_cve",
            "description": "按 CVE 编号查询漏洞详情，返回受影响版本范围与严重等级。",
            "parameters": {
                "type": "object",
                "properties": {
                    "cve_id": {
                        "type": "string",
                        "description": "CVE 编号，例如 CVE-2026-12345"
                    }
                },
                "required": ["cve_id"]
            }
        }
    }
]

response = client.chat.completions.create(
    model="deepseek-flash",
    messages=messages,
    tools=tools,          # ← 菜单随请求发出
)

name 是调用的函数名；description 说明适用任务；parameters 声明参数结构，required 声明必填项。它们帮助模型生成提议，但程序仍要验证实际参数、权限与内容；工具描述不是执行授权。

第 ② 步：模型决策——tool_calls 长什么样

如果模型判断需要查库，它不执行，而是返回一条这样的 assistant 消息（示意结构）：

# response.choices[0].finish_reason == "tool_calls"（而非 "stop"）
msg = response.choices[0].message
# msg.content            → None（这次没有正文）
# msg.tool_calls         → 一条或多条提议：
#   ToolCall(
#     id        = "call_demo_001",        # 本次提议的编号，回填时要对应
#     type      = "function",
#     function  = Function(
#         name      = "search_cve",
#         arguments = '{"cve_id": "CVE-2026-12345"}',   # 注意：是 JSON 字符串
#     )
#   )

三个细节值得盯住：id 是提议的「回执编号」；arguments 是 JSON 字符串不是字典——虽然看着像，直接当字典用会报错；finish_reason 从 "stop" 变成 "tool_calls"，这是程序判断「该走工具分支还是收工」的信号。

第 ③ 步：程序解析与执行——核对嵌在这里

import json

def search_cve(cve_id):
    # 本地实现：查数据库或调外部接口（本课用模拟数据代替）
    return {"cve_id": cve_id, "affected": ">=1.4.0, <1.6.0", "severity": "高危（模拟）"}

messages.append(msg)                        # 先留档：assistant 提议进列表
for call in msg.tool_calls:
    args = json.loads(call.function.arguments)   # JSON 字符串 → 字典
    if call.function.name == "search_cve":
        result = search_cve(**args)         # ← 执行前核对嵌在这之前（见下）
    else:
        result = {"error": f"unknown tool: {call.function.name}"}

把第 2 课的关卡接进来——对 send_report 这类有副作用的工具，执行之前加核对，之后把拒绝也作为结果回填：

ALLOWED_RECIPIENTS = frozenset({"analyst@yourcompany.example"})

def send_report(recipient, summary):
    if recipient not in ALLOWED_RECIPIENTS:               # 执行前核对
        print("AUDIT: denied / recipient_not_allowed")
        return "REFUSED: 收件人不在允许名单内"             # 拒绝也是结果
    return "MOCK_ACCEPTED: 仅模拟通过目标检查，未发送"

# 这是 send_report 分支的示意，不应接在 search_cve 参数后直接运行。
# 这里只演示目标检查；真实系统还需核对任务范围与敏感内容。
result = send_report("attacker@example.com", "模拟报告")

第 ④ 步：结果回填——tool 消息的规矩

messages.append({
    "role": "tool",                  # 新角色：工具结果
    "tool_call_id": call.id,         # 必须与提议的 id 对应
    "content": json.dumps(result, ensure_ascii=False),   # 结果序列化为文本
})

# 然后带着完整列表再次请求：
response = client.chat.completions.create(
    model="deepseek-flash", messages=messages, tools=tools
)

content 通常是字符串（JSON、纯文本、错误码都可以），模型自己会解读。规矩有两条：每条 tool 消息必须通过 tool_call_id 指向它回应的那条提议；提议（assistant 消息）必须先在列表里，结果才能挂上去——先有回执编号，才谈得上对应。

第 ⑤ 步：循环与停止条件

第二次请求后模型可能给出最终回答（finish_reason == "stop"，循环结束），也可能再次提议（回到第③步）。循环必须有停止条件——最常用的是最大轮数守护：

以下为循环伪代码：call_api、execute_with_check、tool_message 是留待实现的封装；结果回填应在处理每条调用的循环内部完成。

MAX_ROUNDS = 8

for round_no in range(1, MAX_ROUNDS + 1):
    response = call_api(messages, tools)
    msg = response.choices[0].message
    reason = response.choices[0].finish_reason
    if reason == "stop":
        print(msg.content)          # 本轮正常结束，不代表回答已验证正确
        break
    if reason != "tool_calls" or not msg.tool_calls:
        print("本轮异常或不完整：", reason)  # 如 length、content_filter
        break                       # 不冒充已完成任务，不自动重试
    messages.append(msg)
    for call in msg.tool_calls:
        result = execute_with_check(call)     # ③ 含核对
        messages.append(tool_message(call, result))   # ④ 回填
else:
    print("已达最大轮数，强制中止")   # 防死循环：模型反复提议时的兜底

为什么需要兜底？模型可能重复提议。最大轮数限制循环次数，但一轮仍可能有多个调用，不能代替每次动作的权限检查、总调用数、时间与费用预算。执行侧负责落实边界，不能仅凭“有上限”断言系统安全。

本地跑通三步连接：不需要网络与密钥

你说过目前没有实际邮件或网络环境——没关系。下面这个脚本把「模型返回的响应」硬编码成一份模拟数据（字段结构与真实响应一致），只演练三步的连接件：解析提议 → 执行 → 回填。存成 mock_tool_flow.py，直接 python mock_tool_flow.py 就能跑：

import json

# 模拟的模型响应：假如模型收到「查 CVE」的请求后返回这条消息。
# 字段结构与真实 Chat Completions 响应一致；不调用任何 API。
MOCK_RESPONSE = {
    "choices": [{
        "finish_reason": "tool_calls",
        "message": {
            "role": "assistant",
            "content": None,
            "tool_calls": [{
                "id": "call_demo_001",
                "type": "function",
                "function": {
                    "name": "search_cve",
                    "arguments": json.dumps({"cve_id": "CVE-2026-12345"}),
                },
            }],
        },
    }]
}

def search_cve(cve_id):
    # 本地模拟数据；真实实现会查数据库或调外部接口
    return {"cve_id": cve_id, "affected": ">=1.4.0, <1.6.0", "severity": "高危（模拟）"}

# ── 请求 1 的 messages（请求时还应附上 tools 菜单，这里省略） ──
messages = [
    {"role": "system", "content": "你是安全情报分析助手。"},
    {"role": "user", "content": "CVE-2026-12345 影响哪些版本？"},
]

# ── 第②步：解析模型返回的 tool_calls（此处来自模拟响应） ──
choice = MOCK_RESPONSE["choices"][0]
msg = choice["message"]
print("finish_reason =", choice["finish_reason"])
call = msg["tool_calls"][0]
print("模型提议：", call["function"]["name"], call["function"]["arguments"])

# ── 第③步：程序执行（真实系统在这层前做执行前核对） ──
messages.append(msg)                        # 先留档 assistant 提议
args = json.loads(call["function"]["arguments"])   # JSON 字符串 → 字典
result = search_cve(**args)

# ── 第④步：结果回填为 tool 消息 ──
messages.append({
    "role": "tool",
    "tool_call_id": call["id"],
    "content": json.dumps(result, ensure_ascii=False),
})

print(json.dumps(messages, ensure_ascii=False, indent=2))
# ── 第⑤步：带着这份四条消息的列表再次请求（真实系统调 API；模拟到此为止） ──

运行后会打印四条消息：system、user、assistant 提议和 tool 结果。这是本例下一次请求的上下文部分，请求还需 model、tools 等参数。脚本固定只有一条合法的查询提议；真实接入还需处理多调用、未知工具、无效参数和执行失败，不能仅接上一次 API 请求就当作完整 Agent。

标注：此脚本为本地模拟，验证的是数据流的形状（谁追加、什么顺序、id 怎么对应），不验证模型行为；接上真实 API 后的表现属第 0003 课之后的实操，待环境就绪验证。

边界与易错点

  • arguments 是 JSON 字符串，不是字典。call.function.arguments 长得像字典，直接 args["cve_id"] 会报 TypeError——先 json.loads。
  • 先追加提议，再回填结果。顺序颠倒或漏掉 assistant 消息，tool 结果就没有对应的提议可挂——接口会拒绝这种序列。
  • tool_call_id 必须用提议里返回的那个 id，不要自己编一个新的；多条提议时逐条对应。
  • 模型可能一次提议多个工具调用（并行提议）。稳妥的写法是像第③步那样用循环逐条处理，而不是只取 [0]。
  • 「模型执行了工具」是错觉。模型只产出提议；执行、核对、留痕都在程序侧。日志里记的执行者应该是你的程序，不是模型。
  • 区分正常结束与异常中断。stop 表示生成正常结束；length 等停止原因不能直接当成任务完成。循环次数、调用数和费用预算分别控制。
  • 只读也需检查。真实查询可能访问敏感数据、把查询发送给外部服务、引入恶意结果或消耗资源；外发报告又增加了输出侧风险。两者都要检查范围，拒绝结果也应按调用编号回填。

练习 1 · 找出三处「连接断点」并修复

下面这段代码想完成「解析提议 → 执行 → 回填」，但有 3 处连接断点（都对应本课讲过的规矩）。找出每一处并写下修法：

import json

messages = [{"role": "user", "content": "查一下 CVE-2026-12345 的影响范围"}]
msg = response.choices[0].message      # 模型刚返回的、含 tool_calls 的消息

# 断点 ①：直接回填结果，没有做"留档"
messages.append({
    "role": "tool",
    "tool_call_id": "call_999",          # 断点 ②：这个 id 是随手编的
    "content": json.dumps({"affected": ">=1.4.0, <1.6.0（模拟）"}),
})

# 断点 ③：把 arguments 当字典直接用
args = msg.tool_calls[0].function.arguments
result = search_cve(args["cve_id"])
messages.append({"role": "tool", "tool_call_id": msg.tool_calls[0].id,
                 "content": json.dumps(result)})

对照图 2 右框的四条消息顺序；对照第③步代码里 arguments 的处理方式；对照 tool_call_id 的来源。

查看答案与解析

断点 ①（漏留档）：回填前必须先 messages.append(msg) 把含 tool_calls 的 assistant 提议放进列表——没有它，tool 结果找不到对应的提议，接口会拒绝这条消息序列。

断点 ②（id 不对应）："call_999" 是编造的；必须用提议里真实返回的 msg.tool_calls[0].id。回填消息靠 id 与提议配对，id 对不上等于结果挂错账。

断点 ③（JSON 字符串当字典）：arguments 是 JSON 文本，args["cve_id"] 直接报错；要先 args = json.loads(msg.tool_calls[0].function.arguments) 再取键。

修复后的顺序：删除提前伪造的 tool 消息 → append(msg) → json.loads → 执行 → append 一条真正对应的 tool 结果。多调用时，每个调用各回填结果，不重复回填同一 id。

常见错误：只找到断点 ③——因为它会直接报错最显眼；①②不抛异常，却在下一次请求时才炸（接口拒绝消息序列），更隐蔽。

本课总结

三句话，把「三步连接」装进口袋：

  1. 连接件是 messages：提议是一条 assistant 消息（tool_calls），结果是一条 tool 消息（tool_call_id 对应），两次调用之间靠程序把列表越拼越长。
  2. 模型只提议，程序才执行：声明（tools 菜单）与执行（含第 2 课的核对）都在程序侧；拒绝也要回填，让模型知道边界。
  3. 循环要带闸：finish_reason=tool_calls 就再走一轮，stop 就收工；最大轮数兜底，防止不收敛的提议无限转。
